## 背景・制約

詳細設計21.6では受付の準備と本人の払戻し承認が別操作だが、基本設計のH01は1行の論理案である。REF-03は技術的障害で返金できない場合も未完了申出を保持する。取引確定Txと申出保存を常に一括でロールバックすると、返金申出自体を失う。HTTP契約とDB担当との境界を明示する必要がある。

## 比較した案

| 案 | 特徴・課題 |
| --- | --- |
| 単一の多用途POST | 呼出し数は少ないが、受付権限/本人承認と準備/金銭成立の分岐が混在する。返金Tx失敗時の申出保持には別の永続化契約が必要 |
| 準備/申出と確定を分離（本提案） | 主体・効果・再開点をoperation単位で定義できる。申出保存だけ成功した中間状態と、操作別のキー/版管理が必要 |

## 提案と理由

H01は受付によるPREPARED作成と本人によるHELD承認に分け、H02/H03/H04は現金交付開始・完了/取消/調査・引継ぎを提供する。返金専用額も同じ処理で元区分を保持する。

R02はREQUESTED申出保存とexecuteによる残高返金確定に分ける。申出保存は金銭を更新せず、同キー再送で同じ申出へ復帰する。返金確定では累計を再検証し、残高・売上・返金・台帳・監査・Outboxを既存要件どおり同一Txに含める。未完了申出の保存Txを金銭成立と表示しない。申出の状態語彙とHTTP分割は今回の補完案で、要件承認済みの語彙としては扱わない。

既存のキー照会は単一取引の応答だけではPREPARED/REQUESTED/引継ぎを復元できないため、transactionまたは現在のresourceを返す案へ拡張する。コマンドの成功と現金/残高返金の完了を区別する。

## 影響・検証方法

FEは本人承認の導線と中間状態の表示、操作別キー/IDの保存、再接続時の一覧・詳細照会が必要。DBは原子的な拘束/解放と元区分、申出の独立保存、元決済を共有する累計排他、権限変更後の照会を確認する。申出Txと確定Txの間で切断しても、同じ申出へ復帰し二重返金しないことをAT-037/043/045/047で検証する。金銭一括Tx要件を変更する提案ではない。

パス・型は[OpenAPI](../design/api/openapi.yaml)、業務規約は[返金API設計](../design/api/refunds.md)を参照する。実動作試験は未実施。
