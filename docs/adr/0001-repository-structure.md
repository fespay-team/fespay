# ADR-0001：単一リポジトリとドキュメント配置

- 日付：2026-09-14
- 状態：初期構成に適用。チームレビューは未実施。
- 関連：要件定義書 第31・32章、DEV-01、DEV-02

## 背景

要件書はFE2人・BE2人・総合1人の5人編成を想定しています。
金銭処理・在庫・注文を整合させ、UIとAPIの契約変更も同時に確認する必要があります。
現在の依頼はチーム開発用のリポジトリ準備であり、アプリの実装は開始しません。

## 判断

GitHub Organizationが所有する単一のprivateリポジトリを初期方針とします。
要件・設計・試験・運用を `docs/` に置き、将来のコードと同じPRで変更できるようにします。
今回は文書とコラボレーション用のファイルを作成します。

## 実装開始時の配置案（未作成）

| パス | 用途 |
| --- | --- |
| `apps/web/` | 来場者・レジ・管理のWeb画面。内部で機能ごとに分割 |
| `apps/api/` | モジュラーモノリスのAPI・認証連携・DBマイグレーション |
| `packages/contracts/` | API契約に基づく共有型・スキーマ。サーバー秘密を含めない |
| `tests/` | アプリをまたぐE2E・負荷・障害試験。単体テストは各コードの近く |
| `infra/` | 開発・試験・公開環境の構成。秘密の実値は保管しない |
| `.github/workflows/` | 文書検査、テスト、依存・秘密情報検査などのCI |

パッケージマネージャー・ワークスペースツール・依存ライブラリの版は今回固定しません。
要件書第31章の基準構成を踏まえ、実装開始時に別ADRで記録します。

## 比較と影響

FE・BE・文書の別リポジトリは権限やリリースを独立させやすい一方、契約変更が複数PRに分かれます。
初期の5人開発では同じ変更を一度にレビューできることを優先します。
規模拡大で分割する場合は依存関係とデプロイ境界を再検討します。
実装開始後は関係するパスだけを対象とするCIで待ち時間を抑える予定です。
