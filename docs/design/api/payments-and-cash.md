## 受付チャージ

1. 現担当grant/MFA、受付QR60s、本人/イベント/期間を確認し、額固定の準備IDを保存。PREPAREDでは現金受領・残高加算はしない。
2. 担当者が本人表示・受領額/付与額を確認して現金を預かる。同じ準備ID・版・額とcash_received_confirmed=trueでcomplete。
3. 正本TxでAVAILABLE加算・取引・台帳・現金受領記録・監査・Outboxを確定する。準備当たり成立は1回。金額変更は未受領取消の後に新準備。
4. 応答不明は元キー/準備IDで照会。受領現金の即返却・再受領・別ID付与を指示しない。未成立が永続確定した調査案件だけから、担当再承認による同じ準備の付与または現金返却記録へ進む。

未受領の取消と、受領後・未成立確定の返却は別API。後者は当該解決案件のNOT_COMMITTEDと受領/返却事実を検証し、受領・返却記録を残してCANCELLEDへ。walletは変えない。返却済み案件の再送では現金をもう一度返さない。

## A/B/C・注文経由の共通決済

| 入口 | 作成/関連付け | 期限と予約 |
| --- | --- | --- |
| A：店の会計QR | 店がCREATED内容を保存しQR発行。本人がtokenを照合し、最初の1人だけbind | 表示300s。未関連付けは予約なし。bind時に必要全予約と180s固定見積 |
| B：本人の支払QR | 店が対象tokenと会計内容を送信しAWAITING_APPROVALへ | 表示60s。token単回関連付け、本人/eventの承認待ち1件。要求/予約180s |
| C：金額型固定QR | 参加本人が店/正額を確認する要求を作成 | 180sの本人確認要求。商品/在庫必須の店では拒否 |
| C商品型・モバイル | 本人の単店舗cartからcheckout | 主催者/店の双方許可＋商品/注文。固定見積/全予約180s |

会計の価格・名称・提供条件は版付きで保存する。通常価格変更は確定見積へ無断適用せず、販売停止は未成立会計を拒否する。A未関連付けの内容変更は旧要求を取消して新要求。新QRの再生成には元内容/価格版/販売可否を再検証する。

本人がexpected_version/content_version/approved=trueを送ると、共通finalizePaymentが本人・最新権限・機能・停止・実時刻・AVAILABLE・必要予約を確認する。wallet・取引・売上・注文・全在庫/予約・台帳・Outboxを同一Txで確定。Q02 approveとO01 ordersは同じ要求の自然一意制約を使い、別経路/別キーでも同一取引/注文へ復帰する。店の会計grantで本人承認を代行しない。

拒否/取消/期限切れは予約全解放と要求終端を一括確定する。表示QRが更新/失効しても関連付け済み180s要求の期限を変えない。期限切れを新しいキーだけで延長しない。新しい確認は商品・価格・在庫・権限を再検証した別要求へ。FEの自動QR更新は前面表示中の有効session・不変内容だけ。

## 譲渡

受取本人は300sの単回QRを発行。送信本人が照合して相手表示/番号・イベント・額・参考送信後残高を確認する準備を保存する。準備はwallet/tokenを消費せず、previewed_at時点の参考値として扱う。

確定は保存済み相手/額/版との一致、両参加・譲渡ON・期間・実時刻・AVAILABLE・token未消費を再検証。送受walletの全額更新・token消費・同一取引/台帳/Outboxを一括確定する。別準備/別キーでも1受取tokenにつき1譲渡。譲渡OFFは未成立にも適用する。成立後の送信者単独取消は受け付けず、受取本人の新譲渡または調査へ。受取/業務照会には送信者残高を返さない。

## 現金訂正・調査・実査

| 操作 | 更新するもの | 必須確認 |
| --- | --- | --- |
| 誤チャージ訂正 | 元本人AVAILABLE相殺、別訂正取引/台帳 | 元額−既訂正額以内、残高十分、専用grant/MFA/理由 |
| 未交付なのにPAIDとした払戻しの訂正 | 元balance_sourceへ元額全額復元、別訂正取引/現金記録訂正 | 同じ元取引の解決案件NOT_HANDED/COMMITTED、1原取引1訂正 |
| 現金調査のresolve | DB結果/現金事実/証跡/理由を監査し案件RESOLVED | 原処理の正本・排他確認。未検出やタイムアウトを未成立証明にしない |
| 訂正に伴う現金返却確認 | 既返却事実・現金記録・状態 | 未返却/返却済みを区別。不明からの復帰は同じ解決案件 |
| 釣銭/投入/引出 | 現物資金移動の独立記録 | 利用者チャージやwalletに混ぜない |
| 現金実査 | 固定snapshotの理論額とactual、差異/案件 | 理論額はサーバー算出、scopeを重複加算しない |

調査resolve単独では残高/拘束/交付を動かさない。RESOLVEDは事実確認の完了で、払戻しや返却の完了ではない。後続のH03 complete、charge complete/cash-return、correction cash-returnが同じ案件を参照し、現在の担当/権限と原処理を再検証する。原Transactionを未成立に戻したり履歴を消したりしない。

現金実査は開始釣銭＋記録受領−交付−返却＋投入−引出。差異=実査−理論。担当scopeは割当先で集計し、EVENT総額へ二重加算しない。記録受理を差異解決にせず、0差異かつ未解決0をイベント完了条件にする。実査時点と確定ログcutoffの対応はDB担当とレビューする。

## 通常残高の失効

公開APIは、設定済みpolicy_version・期限到来・主催者特権MFA・理由でrunを作る。任意額/対象account指定は受け付けない。各wallet/条件版/期限の自然一意で再実行を抑止し、対象AVAILABLE・別失効取引・台帳を原子的に確定する。HELD/REFUND_ONLY/紛争保全額は保持。未実行バッチの遅延を利用した支払/譲渡を拒否する。

run受付や一部walletの処理成功を全run完了と表示しない。INVESTIGATING/remaining>0は未解決として保持する。自動workerの承認保存・起動認証はBEレビュー対象。技術的失効を法的な債権消滅の証明としない。
