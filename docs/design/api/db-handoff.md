## 分担・根拠

API担当はHTTP入力/応答/権限/エラー/再送を定義し、DB担当は[DB・台帳設計](../database/README.md)で論理ER・物理型・制約・索引・マイグレーションを具体化する。ここでは要件上必要な不変条件と照会条件を整理し、DB内部の名称や実装方式は指定しない。既存詳細設計の物理モデルもレビュー前の補完案として扱う。

## 共有して確認する事項

| 接点 | APIから必要な条件 | DB設計との確認事項 |
| --- | --- | --- |
| ID/所属 | eventと必要なshopと対象IDを毎回照合 | 公開UUIDと内部ID、複合FK/一意制約、削除せず履歴を保持 |
| 本人残高 | account/eventの一意口座、3区分を同一時点で返す | available/held/refund_onlyの台帳対応、射影の原子的更新、bigint版の文字列化 |
| 取引 | 永続成立だけSUCCEEDED、返金・訂正は別取引 | 取引種別の全語彙、source_ref対応、本人当事者/店舗の照会範囲。actorだけで受取側履歴を判定しない |
| 要求キー照会 | actor/event/operation/keyで元結果を復元 | 同一scopeの一意性、要求hash、取引と結果の同一Tx、保存期間7年 |
| 最終拒否 | REJECTEDとするのは確定した永続拒否のみ | 拒否結果の保存と遅延要求の再実行防止。記録未検出・未コミットだけならUNKNOWN |
| 認可変更 | 結果再送/照会も現在の権限を検証 | 金銭確定と権限解除のTx順。キー・古いresponse_snapshotだけで個人情報を返さない |
| 履歴 | occurred_atとIDの降順、本人当事者、カーソル | 現行権限で絞り、同時刻の取りこぼしを防ぐ。業務一覧は後続設計 |
| 停止 | 既取引照会と新規処理を区別 | サービス/event/shop/アカウント停止の意味、解除権限、照会継続可否 |
| 期限/在庫 | 期限判定は全必要ロック後の実時刻 | 承認・見積・予約180秒、表示QRとは独立、予約消費/解放の排他 |
| Outbox | Tx内に通知を書き、成功応答はCOMMIT後 | UUID再開位置、配送前後/重複/順序、保持期間。安全に再開できなければresync |

## 未決・次のレビュー

operation名と取引種別、wallet versionの公開方法、本人取引の当事者判定、最終拒否の永続化と再送規約、カーソル/Outboxの安全な再開を優先して合わせる。内部DB名とHTTP名が異なっても明示的なDTO変換で対応し、テーブル構造をそのまま外部APIへ露出しない。

確認後、APIはOpenAPI、DBはDB設計本文に決定を反映し、決定者・PR/ADRを記録する。実装後に同口座同時決済、権限解除競合、コミット直後切断、失効後返金の受入試験で一致を検証する。承認者・日付・PR：未記入。
