## 目的・範囲

[詳細設計](../detailed-design.md)第8・9・21.6・21.7節をHTTP契約へ具体化する。未使用残高の現金払戻しと、元の店舗決済に対する購入返金を区別する。型・パス・必須項目は[OpenAPI](openapi.yaml)が正本候補で、本書には処理の意味と競合条件を記載する。誤チャージ訂正C03・現金調査C04/照合C05は[決済・現金設計](payments-and-cash.md)、返金商品の再販戻しP02は[商品・注文設計](products-orders-reports.md)へ具体化した。

## 現金払戻し

H01の準備と本人承認を分ける。受付担当者が受付用QRで本人を照合してprepareCashRefundを呼び、本人は自分の一覧/詳細から準備内容を取得する。QR解決だけで残高拘束や交付を許可しない。一般来場者は業務担当者としてprepareを呼ばず、approveCashRefundで本人の申出額・元区分・内容版を承認する。

| 操作 | 主体・成立条件 | 効果 |
| --- | --- | --- |
| prepareCashRefund（H01） | 現在の払戻し権限と業務追加認証を持つ受付。本人QR・event・額・元区分・受付を照合 | PREPARED作成。残高拘束も現金交付もしない |
| approveCashRefund（H01） | 対象本人のみ。画面で確認した額・元区分・版と一致。担当資格/業務認証もサーバー再検証 | PREPARED→HELD。元区分から拘束へ移す内部取引・Hold・台帳を同一Tx |
| startCashRefundHandover（H02） | 現在の担当本人と業務追加認証。拘束済み正本と額を確認 | HELD→CASH_HANDING。現金を渡す開始を記録 |
| completeCashRefund（H03） | 現在の担当本人。交付済み/未交付の事実を確認、不明なら調査 | PAIDで拘束減算と交付台帳。CANCELLEDで元区分へ解放。INVESTIGATINGは拘束維持 |
| handoverCashRefund（H04） | 主催者または払戻し管理者。新担当の現在の資格を照合 | 旧/新担当・理由・時刻を監査。額・元区分・拘束・交付状態は変更しない |
| 一覧・詳細（H01/H04/C02） | 本人、現在の担当、管理者を範囲別に認可 | 再読込・新端末・引継ぎ後も正本から復帰 |

AVAILABLEは通常払戻しON/期間内、REFUND_ONLYは主催者の精算用受付を別に検証する。通常払戻しOFF・受付終了・失効だけで返金専用額の交付を拒否しない。両区分の混合申出はせず、本人/eventで未完了処理は合わせて1件。本人承認時の元区分は以後固定し、未交付取消でREFUND_ONLYを支払可能額へ変換しない。

HELDから5分無操作で警告、30分で調査一覧に出す。CASH_HANDING以降の未完了は即座に調査対象として表示するが、時間経過で残高を自動解放・現金を再交付しない。INVESTIGATINGからPAID/取消に進む場合、同じ払戻しの解決済み調査案件をresolution_case_idで参照し、理由・交付事実の証跡をサーバー照合する。調査案件はC04 resolveで事実と証跡だけを確定する。[決済・現金設計](payments-and-cash.md)の後続commandが同じsource/caseを照合し、未確認の交付を解決扱いにしない。

新規準備/拘束/未交付現金移動は必要な停止・受付条件を適用する。開始後の通常受付終了でも安全な完了・未交付取消・調査を継続する。緊急停止中も既交付のPAID記録・未交付取消・調査・既処理照会は許可する。PAIDの誤操作訂正は別取引であり、PAID→CANCELLEDや無条件の残高復元は提供しない。

## 店舗決済の購入返金

R02を申出の永続保存と残高返金の確定へ分ける提案。UIの一度の返金確認から2操作を順番に呼べるが、各operationは別のキーを送信前に保存する。利用者が返金額を再承認する仕組みを追加するものではなく、主催者/店舗返金権限者の理由付き操作である。

| 操作 | 主体・成立条件 | 効果 |
| --- | --- | --- |
| createPurchaseRefundRequest（R02） | 主催者または元店舗の返金権限者、業務追加認証、理由。元決済の会計方式と対応する入力 | REQUESTEDを永続保存。残高/売上/在庫は動かさない |
| executePurchaseRefund（R02） | 現在の返金権限と業務認証、保存済み申出の版・内容、元決済と返金累計を再検証 | 返金額加算・売上減算・返金明細・別取引・台帳・監査・Outboxを単一Tx |
| 一覧・詳細（R02追加案） | 元支払者本人、対象店舗の現在の返金照会権限、主催者を範囲別に認可 | 未完了・調査・最終拒否・成立を区別して復帰 |

金額会計では額を指定し、商品明細会計では元の注文明細と数量を指定する。商品IDだけでは同一商品を別単価で買った明細を一意に選べないため、元注文明細IDで識別する。単価・返金額・返金先・本人IDはクライアントに指定させない。商品明細へ任意金額を併記した要求、金額会計への商品明細指定、同じ元明細IDの重複は拒否する。

申出保存は返金可能枠を予約しない。executeで元決済・返金明細をロックし、既成立返金累計と対象数量を再計算する。元決済額/数量を越えたら全体拒否し、上限までの部分成立は行わない。別キー・別担当の並行要求でも共通の元取引で排他する。返金先は確定時にサーバーがAVAILABLE/REFUND_ONLYを選び、申出保存後の販売終了や失効も反映する。

通常払戻しOFFだけで購入返金を省略しない。緊急停止中は申出・照会を保持し、価値移動は主催者の精算専用再開後に行う。元決済の日時・額・支払者・注文明細は不変。返金による在庫自動復元も行わず、再販売確認・理由・返金済み数量の再検証を行うP02は別契約とする。

REQUESTED/INVESTIGATINGは返金未完了。SUCCEEDEDはCOMMIT済みの返金取引必須。技術エラーは記録できれば原因コード付きINVESTIGATINGへ進め、記録不能でも元REQUESTEDと要求キーを残す。未コミット/記録未検出を最終拒否にしない。累計超過等の永続的な業務拒否が確認できる場合だけREJECTEDを保存する。既SUCCEEDEDから申出状態を巻き戻さない。

## 再送・認可・競合

本書の払戻し/購入返金POSTにCookie、CSRF、Origin、操作ごとの現在の認可、冪等キーを要求する。更新済みレコードはexpected_versionを検証する。同キー再送では内容hash照合を現在の照会認可の後に行い、同じ効果/IDを返す。保存時の旧版を再検証して成功を拒否せず、現在のリソース状態を返す。異なる内容・別リソースIDで同じoperation/keyは409。

キー照会のSUCCEEDEDは「そのコマンドの効果が永続成立した」意味に拡張する。prepareのresource=PREPARED、申出保存のresource=REQUESTEDでもコマンドは成功し得る。FEは現金交付にCashRefund.status=PAID、購入返金にPurchaseRefund.status=SUCCEEDEDと取引IDを確認し、HTTP 200/201やコマンド状態だけで返金済み表示しない。

準備を開始した担当者のキーは利用者側で流用しない。本人はmine一覧/詳細で発行済み準備に復帰する。旧担当者の権限解除後はキー照会も拒否し、新担当は引継ぎ後のresource IDで照会する。表示名/照合番号は本人・許可された担当範囲へだけ返す。
