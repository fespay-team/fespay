# 要件定義

## 文書の役割

| 役割 | 文書 | 扱い |
| --- | --- | --- |
| 現行要件書 | [EPP-REQ-001](event_payment_requirements.md) | 設計・実装・試験が通常参照する安定パス。承認済みの変更だけを反映する |
| 受領原本 | [EPP-REQ-001 v0.1（統合基準版）](event_payment_requirements_integrated_v0.1.md) | 2026-09-14に受領したMarkdownを内容変更なしで保存する原本。編集しない |
| 変更記録 | [changes.md](changes.md) | 提案、レビュー、承認、却下と影響範囲を変更ID単位で記録する |

初回の現行要件書は受領原本v0.1と同一内容で作成した。現行の本文版もv0.1である。今後の通常参照は現行要件書とし、受領時の内容や取込み事実を確認する場合だけ受領原本を参照する。記載された実装・試験・外部確認は、このリポジトリの作成によって完了したものではない。

## 改訂ルール

1. 要件変更を提案するときは変更IDを採番し、[changes.md](changes.md)に状態、理由、内容、影響要件ID、関連受入試験ID、Issue/PRを記録する。
2. 提案中・レビュー中は現行要件書を変更しない。設計・API・DB・UI・受入試験への影響を差分としてレビューする。
3. 承認時は、同じPRで[変更記録](changes.md)を「承認済み」にして決定者・決定日を記録し、[現行要件書](event_payment_requirements.md)の本文と文書内の版・改訂日を更新する。
4. 却下した変更は状態と決定を記録し、現行要件書には反映しない。
5. 通常の改訂履歴はGitのcommitとPRで追跡する。改訂ごとに本文全体を複製したv0.2、v0.3などのファイルは追加しない。

要件IDは承認済み要件の追跡キーとして維持する。変更時は関連する設計書・受入試験・Issue/PRの参照も同時に更新する。

## 版固定スナップショット

提出、承認、監査など、特定時点の完全な文書をGit履歴とは別に固定パスで再現する必要がある場合に限り、承認後の現行要件書から `snapshots/EPP-REQ-001_vX.Y.md` を作成できる。作成時は目的、対象commitまたはtag、作成日、SHA-256をこのREADMEまたは対応する変更記録に残す。

スナップショットは作成後に編集せず、現行要件書へのリンク先にも使わない。通常の版比較はGit履歴を使い、日常の改訂のためにスナップショットを作らない。

## 旧方式で作成済みのレビュー資料

[EPP-REQ-001 v0.2レビュー案](event_payment_requirements_integrated_v0.2.md)は、本ルールへ移行する前に作成済みのCR-0001用作業資料である。既存作業を保全するため内容を変更せず保持するが、現行要件書・承認済み版・版固定スナップショットのいずれでもない。今後はこのファイルを更新・複製せず、CR-0001の状態と決定は[changes.md](changes.md)で管理する。
