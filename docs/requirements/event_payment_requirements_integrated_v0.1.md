### 要件の決め方
「確定方針」はユーザーの明示回答、「補完採用」は今回委任された推奨仕様を意味する。特記がない具体的な時間・操作・技術構成は補完採用として本書へ組み込み、個別回答待ちには戻さない。「公開前ゲート」だけは外部確認・実測・契約等の証拠が必要であり、文書作成で確認済みにはしない。

GOV-01　初期必須機能、画面、権限、状態遷移、データ不変条件、受入試験を本書で定義する。API全項目・物理ER図・完成UI・運用手順書は後続の設計成果物とし、本書の制約を満たすこと。

GOV-02　2027年1月20日までに機能完成、統合試験、公開機能、運用・利用手順、試験報告、発表資料を用意する。「一般公開できる機能がある」と「実金銭運用の法務・運営条件が確認済み」は分けて評価する。

GOV-03　実金銭公開の条件が未達の場合は、未達を明示して模擬残高の公開デモに限定する。これは一般公開サービスという目標の達成を自動認定するものではない。実運用実績や性能を捏造しない。

GOV-04　完成後の継続は需要・状況を見て判断する。ただし実金銭を扱い始めたイベントは、未解決の残高・返金・問い合わせを放置して終了できない。運営責任者と終了手順を公開前に確定する。

## 02　対象範囲・用語・設計規模

### 初期必須の範囲
| 領域 | 初期に実装する内容 |
| --- | --- |
| 参加・主催 | 共通アカウント、メール＋Google認証、イベント作成、一覧掲載と参加条件の独立設定。 |
| 店舗・人員 | 主催者、運営、店舗管理者、レジ担当、来場者。複数店舗・同一店舗の複数レジ。 |
| 金銭 | 現金チャージ、残高、QR決済B/A/C、同イベント内譲渡、現金払戻し、購入取消・部分返金、失効。 |
| 販売 | 金額入力、商品選択、商品単位在庫、注文管理、双方許可によるモバイルオーダー。 |
| 管理 | 売上・現金の照合、CSV、監査ログ、担当者招待、利用停止、障害時の結果確認。 |
| 提供 | インストール不要Web、スマホ優先の来場者・レジUI、PC優先の管理UI。クラウド・インターネット接続前提。 |

SCP-01　LAN内完結、会場サーバー、会場ネットワークからの接続元制限、クラウドとの方式切替は完全に対象外。会場の通常Wi-Fiや携帯回線の利用は妨げない。

SCP-02　NFC、ストア配布ネイティブアプリ、銀行等への送金連携は将来・余力対応。換算率変更、特典、無料配布、イベント間残高移動、スマホなし代替、オフライン決済後同期、原材料在庫、後払い、複数店舗一括会計、外部カードチャージは初期対象外。

SCP-03　「上限なし」は金額の業務上の上限を指す。取引件数・画像サイズ・API頻度・商品明細数など、資源保護の上限までなくす意味ではない。上限の設定画面は初期に作らない。

| --- | --- |
| 1イベントの累計参加者 | 10,000人 |
| 1イベントの店舗数 | 100店舗 |

### 用語
「決済」は利用者残高から店舗売上へ価値を移す処理。「現金払戻し」は未使用残高を現金で返す処理。「購入取消返金」は元決済を指定して元の利用者へ戻す処理。「譲渡」は同イベント内利用者間の残高移動。「台帳」は成立した金額増減の正本。「拘束」は他の支払いに使えないよう確保すること。「正本」は最終的な根拠となるデータを意味する。

## 03　責任分担・ロール・操作権限

ROL-01　業務上の現金管理者は各イベント主催者とする。主催者は受付現金、利用者への払戻し、出店者への精算を担当する。プラットフォームは残高や取引を記録するが、初期版で現金の受領・保管・送金を代行しない。法的な発行主体・契約関係は第33章で確認する。

| 操作 | 主催者 | 運営担当 | 店舗管理者 | レジ担当 |
| --- | --- | --- | --- | --- |
| イベント設定・開催制御 | 可 | 不可 | 不可 | 不可 |
| 運営・店舗管理者の任命 | 可 | 不可 | 不可 | 不可 |
| レジ担当の管理 | 全店舗 | 不可 | 自店舗 | 不可 |
| 現金チャージ・払戻し | 可 | 個別許可 | 不可 | 不可 |
| 会計・注文受取 | 全店舗 | 個別許可 | 自店舗 | 自店舗 |
| 商品・価格・在庫変更 | 全店舗 | 個別許可 | 自店舗 | 個別許可 |
| 購入取消・残高返金 | 可 | 個別許可 | 個別許可 | 個別許可 |
| 売上・CSV | 全店舗 | 個別許可 | 自店舗 | 個別許可 |
| 自分の支払承認・譲渡 | 本人分 | 本人分 | 本人分 | 本人分 |

ROL-02　来場者は本人の残高・履歴・注文だけを閲覧し、本人分の支払い・譲渡・払戻し申出を行える。他者の金銭操作を承認できない。主催者であっても本人の支払承認を代行しない。

ROL-03　認可キーはアカウント＋イベント＋必要に応じ店舗＋操作。APIごとに所属と権限を検証し、ID書換えや他イベントの権限流用を拒否する。画面の非表示だけを制御としない。[S1]

ROL-04　兼務を許可するが、レジ・受付では現在のイベント、店舗、業務モードを常時表示する。会計・チャージ・払戻しの未完了中はモード切替を止め、確定結果の確認か安全な取消を先に行う。

ROL-05　プラットフォーム管理者はサービス・アカウント・イベントの停止と監査を担当する。通常画面に残高の任意編集機能を設けない。特権調査は理由、操作者、対象、時刻を残す。自分への業務権限追加は禁止する。

ROL-06　権限解除後の新規処理は拒否する。既成立取引は保持するが、業務照会も現時点で権限を持つ者に限る。旧担当者には本人の来場者取引以外の閲覧権限を残さない。競合時はDB内の認可検証・確定順で判定し、古い画面やセッションの権限を信頼しない。

## 04　スタッフ招待・委任・管理者交代

STF-01　主催者が運営担当・店舗管理者を招待する。店舗管理者は自店舗のレジ担当のみ招待・権限変更・解除できる。付与範囲は「主催者の許可範囲」かつ「付与者自身が保有する権限」の共通部分とする。レジ担当には招待権限を付与できない。

### 招待の具体仕様
| 項目 | 採用値・動作 |
| --- | --- |
| 宛先 | 既存のサービス内アカウントID、または確認済みメールで照合する招待先メール。未登録者は登録後に受諾する。 |
| 配布 | 招待URLのコピーと、対象者のアプリ内招待一覧を必須。通知メールは補助とし、メール未着だけで招待を失わない。 |
| 有効期限 | 発行から72時間。期限境界はサーバー時刻。延長ではなく再発行し、同一対象・同一役割の旧未受諾招待を失効させる。 |
| 秘密 | 256ビット相当の乱数トークン、検証用ハッシュ保存、一回限り。ログ・CSVに秘密を出さない。 |
| 受諾 | ログインした本人がイベント・店舗・権限を確認して受諾。受諾前に業務権限はない。 |
| 再検証 | 受諾時に発行者の現役ロール、主催者設定、権限範囲を再確認。権限が不足した場合、黙って縮小せず再招待を求める。 |
| 重複・競合 | 同一本人の並行受諾は1回だけ成立。権限変更はversionを照合し、競合時は409と最新状態を返す。 |

STF-02　店舗管理者の交代・解除後も、受諾済みレジ担当の所属・個別権限は維持し、主催者または新管理者が管理を引き継ぐ。付与者IDは監査情報であり、受諾済み権限の恒久的な親子依存にはしない。旧管理者自身の権限は解除する。

STF-03　旧管理者が発行した未受諾招待は無効化する。管理者の権限縮小でも受諾済み担当者を自動停止しないが、主催者による店舗全体の禁止設定・個別解除は直ちに優先する。新管理者は自分が持たない権限を追加・変更できず、既存権限の見直しは主催者へ依頼する。

STF-04　管理者不在の店舗は主催者が管理を引き継ぎ、既存レジを自動停止しない。同一店舗の複数管理者を許可し、全員の任命は主催者が行う。イベント所有者は1アカウントとし、交代には旧所有者の再認証と新所有者の受諾を要求する。

STF-05　権限解除で共通アカウント、本人の来場者残高、過去取引、他所属を削除しない。招待・受諾・変更・拒否・解除・交代の前後値、操作者、理由、時刻を監査へ記録する。

## 05　認証・アカウント連携・復旧

ACC-01　メールアドレス＋パスワードとGoogleログインの両方を提供する。片方だけで利用可能とし、Google利用者にローカルパスワードを強制しない。金銭・主催者操作は確認済みメールを持つ有効アカウントに限定する。

| 項目 | 補完採用する仕様 |
| --- | --- |
| パスワード | 15～128文字。貼付け・パスワード管理ツールを許可。既知の弱いパスワードを拒否し、不要な定期変更を強制しない。 |
| メール確認 | 24時間有効、一回限り。再送は60秒間隔以上、同一宛先5回／時。 |
| 再設定 | 30分有効、一回限り。登録有無を外部へ明示せず、完了後に全既存セッションを失効。 |
| セッション | 最終利用から7日、発行から30日を上限。サーバー管理とし、ログアウト・全端末ログアウト・失効を反映。 |
| Cookie | Secure、HttpOnly、SameSite=Laxを基本とする。クロスサイト処理は別途CSRF・Origin検証。 |
| メール変更 | 既存方法での再認証＋新メール確認。旧メールへ変更通知し、衝突する既存アカウントへ統合しない。 |
| 表示名 | 1～40文字。改行・制御文字は禁止。内部の不変account_idとは区別する。 |

ACC-02　Google認証結果はサーバーで署名、issuer、audience、有効期限、nonce等を検証し、検証済みsubを外部識別子として扱う。メール申告だけで本人認証しない。[S2]

ACC-03　認証方法の追加は、既存アカウントの再認証後に追加先でも認証する。メール一致だけの暗黙統合を禁止する。Better Authを基準構成とし、disableImplicitLinkingを有効にする。手動連携と新規登録の境界を受入試験で確認する。[S3]

ACC-04　Googleだけの利用者がパスワードを追加する場合は、Googleで再認証し、同じサービス内IDに資格情報を追加する。別々に作成済みのアカウント間で残高・履歴を統合する機能は対象外。最後の有効な認証手段の解除を拒否する。

ACC-05　新端末でログインできれば同じ参加イベント・残高・履歴へ復帰する。メールや全認証手段を失った場合、表示名だけで復旧させない。主催者は共通ログインをリセットできず、サポート案件として扱う。

ACC-06　パスワードは平文・可逆暗号で保存しない。認証基盤のscryptまたは同等以上の安全なハッシュ設定を用い、実行環境で処理時間を測る。再設定・セッション失効は既存認証基盤を利用する。[S4][S5]

## 06　重要操作の追加認証・利用停止

SEC-01　主催者、運営の金銭担当、返金権限者、プラットフォーム管理者は、重要操作前に追加認証を完了する。TOTP認証を基準とし、一般来場者の追加認証は任意とする。Googleログインだけで追加認証済みとは扱わない。

### 業務セッション
| 対象・操作 | 要求する確認 |
| --- | --- |
| チャージ・現金払戻し・購入取消返金 | 業務開始時の追加認証。有効8時間、無操作30分で再確認。各金額は毎回確認画面で承認。 |
| 権限付与、主催者交代、失効実行、保護条件変更、サービス停止 | 5分以内の追加認証＋理由入力。 |
| 通常レジ・注文の受渡し | 通常セッション＋最新の業務権限。追加認証必須対象を兼務する場合はその条件も満たす。 |
| 2段階認証の登録・解除 | 現在の方法で再認証し、設定したコードで登録確認。秘密鍵を平文ログへ出さない。 |

SEC-02　TOTPは30秒周期、前後1周期まで、同一コードの再利用不可。試行5回／5分、超過時15分停止。回復コードは一回限りの10個を発行しハッシュ保存する。回復コード再発行時は旧コードを失効させる。コードをすべて失った場合、口頭申告だけで業務認証を解除しない。

SEC-03　Better Authの2FA機能を使う場合、OAuth系ログインが既定では同じ2FA制御を受けない点を考慮し、業務APIでも追加認証完了を検証する。Googleのみの利用者の登録には対応設定と再認証フローを用いる。ライブラリ導入だけを合格条件としない。[S6]

SEC-04　アカウント停止とイベント内の利用停止を分離する。停止後は新規決済・譲渡等を拒否し、残高と成立済み記録は保持する。本人の履歴・問い合わせ手段は原則残し、不正アクセス時には本人確認後の専用窓口に切り替える。

SEC-05　停止・紛失端末で開始した未成立の支払要求は承認時に再検証して拒否する。成立済み取引は、端末を無効化したことだけで取消さない。現金交付中の処理は担当変更を記録して調査・完了させる。

SEC-06　権限者による不正チャージを、残高計算だけで防げるとは主張しない。現金受領記録、担当者別集計、毎日の現金実査・差異確認、理由付き訂正と監査で検出・追跡する。共有アカウントは禁止する。

## 07　イベント作成・一覧掲載・参加

EVT-01　有効アカウントは主催者としてイベントを自分で作成できる。個別のプラットフォーム審査は置かない。必須項目・利用条件・期間整合の自動検証は行う。サービス全体の実金銭公開ゲートを満たす前に、実金銭取引だけを先行開放しない。

| 項目 | 入力・表示仕様 |
| --- | --- |
| イベント名 | 1～100文字。 |
| 説明 | 0～2,000文字。HTML直接入力は不可。 |
| 主催者表示名・会場 | 各1～100文字／1～200文字。会場住所・位置情報は必要な範囲のみ任意掲載。 |
| 問合せ先 | 確認済みメールまたはHTTPSの問い合わせURLを最低1つ。公開用連絡先をログインメールと分離。 |
| 開催期間 | 開始・終了必須、開始＜終了。表示はAsia/Tokyo、保存はUTC。 |
| 一覧掲載 | 掲載／非掲載。作成時は非掲載。参加方式とは独立。 |
| 参加条件 | 公開／参加パスワードあり。初期選択は公開だが公開操作時に確認を要求。 |
| 参加パスワード | 8～64文字。設定時のみ表示、ハッシュ保存、後から再表示しない。 |

EVT-02　掲載＋公開、非掲載＋公開、掲載＋パスワード、非掲載＋パスワードの4通りを許可する。一般一覧は公開中かつ掲載対象のみ。検索対象は名前、開催日、会場文字列で、既定順は開催開始日・IDの昇順、1ページ20件・最大100件とする。

EVT-03　非掲載イベントは一般一覧API・検索・サイトマップに含めずnoindexを付ける。URLを知る人には案内を表示するため、非掲載をアクセス制御と呼ばない。掲載解除は自社APIに即時反映し、公開キャッシュは60秒以内に失効させる。外部検索の即時削除は保証しない。

JOIN-01　ログイン→条件表示・同意→必要時の参加パスワード検証→参加確定。参加と残高口座はaccount_id＋event_idで一意。参加だけで残高・業務権限を付与しない。店舗QRへの直アクセスでも同じ確認を行い、完了後は元店舗へ戻す。

JOIN-02　参加条件・パスワード変更は以後の新規参加へ適用する。既参加者に再入力を強制せず、残高・履歴・権限を残す。誤入力はアカウント＋イベント単位で10回／10分、超過時15分待機。同一会場IPの全員を一律停止しない。

JOIN-03　退会は残高・拘束・未完了注文がすべて0の場合のみ通常受付し、参加記録は履歴として保持する。残高保有中は問い合わせ・精算へ案内する。イベント削除で利用者の共通アカウントを削除しない。

## 08　イベントの状態・日時・初期設定

EVT-04　イベント状態と取引ごとの受付期間を両方確認する。表示上の「開催中」だけでは金銭操作を許可しない。期間は開始を含み終了を含まない。サーバー時刻で判定し、端末時刻の変更を無視する。

| 状態 | 許可する主な業務 |
| --- | --- |
| 下書き | 主催者の設定と担当者準備。一般参加・金銭取引は不可。 |
| 公開・準備中 | 案内・参加・商品閲覧。設定済み期間内なら事前チャージ可能。販売開始前の支払いは不可。 |
| 開催中 | 各受付期間内のチャージ、決済、譲渡、注文、返金。 |
| 販売終了 | 新規決済・注文・譲渡を停止。既存商品の受渡し、購入取消、現金払戻し、集計は継続。 |
| 精算中 | 未解決取引・現金差異・払戻し・残高処理の整理。 |
| 完了 | 新規通常処理は不可、履歴・CSV・問い合わせは閲覧可能。正当な訂正は理由付き再開処理へ。 |

| 設定 | 作成時の推奨初期値・変更条件 |
| --- | --- |
| チャージ期間 | 開催開始～開催終了。事前チャージを行う場合は主催者が開始を早める。 |
| 支払い・譲渡期間 | 開催開始～開催終了。譲渡終了は支払終了を越えない。 |
| 譲渡 | 初期OFF。主催者が明示的にONにする。 |
| 未使用残高払戻し | 初期ON。受付期間は開催開始～終了2時間後。場所・受付体制の確認必須。 |
| 残高失効 | 初期は自動失効なし。ON時は日時と条件を初回チャージ前に指定。払戻し終了より前に失効させない。 |
| 店舗機能 | 金額入力・B/A方式はON、固定QR決済・商品・在庫・注文・モバイル注文は選択式。 |
| モバイル注文 | 主催者・店舗の両方がOFFで開始。双方ON＋商品・注文有効時だけ利用可。 |
| 金額上限 | 業務上なし。設定画面なし。 |

EVT-05　初回チャージ後は払戻しON→OFF、受付期間短縮、残高失効の新設・前倒し等、既存残高に不利益な変更を禁止する。延長・払戻し追加など利用者に有利な変更は理由・版を記録して許可する。条件の履歴はチャージ時の台帳から参照できる。

EVT-06　払戻し期限が過ぎても、未処理の払戻し拘束や取消返金の請求を自動消去しない。残高・未解決現金処理・未完了注文・未処理返金がある場合は「完了」にできない。非公開化で処理を隠さない。

## 09　店舗設定・機能依存・停止制御

CFG-01　主催者は機能ごとに「禁止・任意・必須」を設定する。店舗は任意の機能だけON/OFFを選べる。主催者の禁止は店舗設定より優先し、必須は店舗から解除できない。主催者の変更で矛盾が発生する場合は、影響店舗と必要操作を表示して保存を拒否する。

| 機能の組合せ | 検証条件・扱い |
| --- | --- |
| 商品・在庫を必須 | 商品明細のない金額入力決済を禁止。APIでも拒否。 |
| 在庫管理 | 商品機能を必須とし、在庫対象商品だけ数量を引当てる。材料・セット構成の自動分解は対象外。 |
| モバイル注文 | 主催者許可＋店舗許可＋商品機能＋注文管理が必要。 |
| 固定QRで金額入力 | 金額管理店舗かつ主催者・店舗がC方式を許可した場合だけ可能。 |
| 固定QRで商品選択 | 商品・在庫管理店舗では、モバイル注文が有効な場合だけ支払いまで可能。無効なら店舗案内のみ。 |
| 注文管理OFF | 商品明細や取引は保存するが調理・受取の進捗管理UIは使わない。対面会計はその場で渡す運用。 |
| 全QR方式OFF | 営業状態へ移行できない。停止する場合は店舗受付停止を使用する。 |

CFG-02　主催者・店舗は新規注文受付を一時停止できる。新規決済・在庫予約は拒否し、既成立注文の受渡し・返金・履歴は処理できる。既存の未承認支払要求は停止時に取消し、在庫予約を解放する。成立済み取引には遡及しない。

CFG-03　緊急停止は別フラグとして設け、通常の期間・条件変更と分離する。主催者はイベント全体、店舗管理者は自店舗を停止できる。プラットフォーム管理者はサービス全体も停止できる。

CFG-04　緊急停止中は新規チャージ・決済・譲渡・払戻し開始を止める。成立結果照会、監査、既成立商品の安全な引渡し、すでに現金を渡した払戻しの完了記録は許可する。返金など新たな価値移動は主催者が「精算専用再開」を選んでから実行する。

CFG-05　店舗名は1～100文字、説明0～1,000文字。取引のある店舗は物理削除不可、閉店・非公開として保持する。QRの改ざん・紛失時は公開識別子を再発行して旧URLを無効化できる。

CFG-06　主催者や店舗が変更できるのは機能設定・商品・在庫・受付条件であり、画面レイアウトの自由編集や独自ワークフロー作成は初期に含めない。禁止機能をAPI直接呼出しで復活させない。

## 10　金額上限なし・残高の定義

MNY-01【確定方針】保有残高、1回のチャージ、1回の決済、1回の譲渡、1日の譲渡に業務上の金額上限を設けない。旧版の「サービス上限以内でイベント上限を設定する」仕様・画面・上限判定試験は初期対象から撤回する。隠れた金額閾値を実装しない。

MNY-02　金額は1円単位の正の整数。現金1,000円の受領に対して1,000円を付与し、手数料控除、換算、無償加算、割引ポイントを行わない。0円決済・負数・小数・NaN・Infinityを拒否する。無料商品を残高の0円決済で処理する機能は対象外。

### 技術的な表現と検証
| 項目 | 補完採用する仕様 |
| --- | --- |
| 金額の通信形式 | JSONの10進数字文字列。例 amount_yen="1500"。符号、指数表記、小数点、カンマをAPI入力で認めない。 |
| 計算・保存 | TypeScriptではBigInt等の整数処理、DBはNUMERIC(30,0)を基準とする。浮動小数点へ変換して計算しない。[S7] |
| 技術的な入力範囲 | 1～30桁。これは桁あふれ・資源保護の表現限界であり、イベントの金額上限とは区別する。UIでは円の全文字を表示し省略表記だけで承認させない。 |
| 境界超過 | 取引途中や合計で表現範囲を超えたら全体を確定せず明示エラー。自動分割、丸め、上限までの部分処理は禁止。 |
| 集計 | 複数口座の集計は十分な精度のNUMERIC等で計算。集計の桁数を1取引の入力制限で切り詰めない。 |

WAL-01　残高口座はaccount_id＋event_idで一意。他イベント残高、店舗売上、主催者の現金を来場者の利用可能残高へ混在させない。

WAL-02　画面には「支払い可能額」「払戻し手続中」「購入取消の返金専用額」を分けて表示する。支払い・譲渡で使えるのは支払い可能額だけ。払戻し拘束と返金専用額を空き残高として二重に使わせない。

WAL-03　金額が大きくても本人承認、現金確認、権限、残高不足、受付時間、在庫、重複防止を省かない。利用者の残高は負数にしない。技術エラーで取消返金が完了できない場合も、元決済と未払の返金申出を残して調査し、返金済みと偽表示しない。

WAL-04　「無制限」は実金銭運用の安全性・適法性の証明ではない。譲渡と現金払戻しを含む法的整理は公開前ゲートに残す。[S8]

## 11　現金チャージ・誤入力訂正

CHG-01　チャージ権限を持つ運営が、来場者の受付用QRから対象者を特定する。受付用QRは60秒有効の用途限定トークンとし、支払・譲渡・ログインの承認には流用できない。対象イベント、表示名、短い照合番号を双方で確認する。

### 通常フロー
| 順序 | 操作と成立条件 |
| --- | --- |
| 1 | 権限・業務追加認証・受付期間を確認。利用者を特定し、取引の準備IDを発行する。 |
| 2 | 受領予定額を入力。確認画面にイベント、相手、現金受領額、付与額を大きく表示する。 |
| 3 | 現金を預かり、担当者が「現金受領確認」を実行する。現金受領前の付与は禁止。 |
| 4 | サーバーが同額の残高加算、チャージ取引、台帳、監査を一括確定する。 |
| 5 | 担当者と利用者が取引ID・額・確定時刻・更新残高を確認する。利用者側もサーバー記録を再取得する。 |

CHG-02　同じ準備ID・冪等キーの再送は1回だけ付与する。別金額で同一キーを再送したら409。金額変更は未成立の準備を取消して、現金の扱いを確認した上で新しい準備を作る。

CHG-03　現金を受け取った後に通信が切れたら「結果確認中」とし、現金をすぐに返却・再受領・別IDで付与しない。取引IDと現金受領事実を控え、復旧後に同じ結果を照会する。サーバー未成立が確定した場合に限り、再承認して再処理または現金返却を行う。

CHG-04　現金受領とDB更新は同一トランザクションにできない。受付の現金不足・過剰、入力誤り、未完了処理を差異案件として残す。システム残高の一致だけで現金実査が不要とはしない。

CHG-05　誤チャージの通常訂正は元の成立チャージを指定し、主催者または専用訂正権限者が理由・対象額を入力する。訂正額は元額から既訂正額を引いた範囲まで。利用者の利用可能残高から同額を相殺し、現金返却状態も別に記録する。相殺と台帳は一括確定する。

CHG-06　誤チャージ分が既に消費・譲渡され残高が足りない場合、自動回収や負残高化、他利用者からの巻戻しを禁止する。元チャージを残し、主催者の調査・現金差異案件として管理する。差異解消前はイベント完了を認めない。

## 12　QR決済B方式：利用者QRを読む

PAY-B01【標準方式】店員が会計を作成し、来場者が表示する支払用QRを店舗のスマホで読み取る。店舗が作成した支払要求を本人が確認・承認してから引き落とす。QR読取りだけでは決済成立にしない。

| 順序 | 店舗側 | 来場者側・サーバー |
| --- | --- | --- |
| 1 | 金額入力または商品選択、数量・合計確認。 | 来場者が対象イベントの支払画面を開く。 |
| 2 | 支払用QRを読み取る。 | 60秒有効の支払用QRを表示。金額や永久的な認証秘密はQRに含めない。 |
| 3 | 対象者を確認し要求送信。 | 支払要求を対象者へ関連付け、確認画面に店舗、イベント、金額、商品明細を表示。 |
| 4 | 承認待ちと期限を表示。 | 本人が「支払う」または「拒否」。指紋等の端末機能は必須とせず、ログイン本人の明示承認を使う。 |
| 5 | サーバー成立結果を表示。 | 残高・売上・注文・在庫を一括確定し、双方が同一取引IDの成立結果を確認。 |
| 6 | 商品引渡しまたは調理へ進む。 | 残高・履歴を再取得する。 |

PAY-B02　QRはevent_id・purpose・有効期限を持つランダムトークンへの参照とし、受取用・受付用・支払用を区別する。利用者本人に紐付けるのはサーバーで行い、QR値から残高を推定できないようにする。

PAY-B03　同じ支払用QRが複数店舗から使われた場合、最初の有効な会計への関連付けだけを受理する。別の会計にはQRを再発行する。読取済みQRが表示更新で失効しても、既に関連付けた支払要求は独自の120秒期限内で承認できる。

PAY-B04　1利用者・1イベントのB方式承認待ちは1件。別要求は「別の会計を確認中」と返し、既存要求を確認・拒否・期限切れにしてから作成する。複数端末で同じ要求を承認しても成立は1件。

PAY-B05　支払画面を開いている間に更新情報を受け取る。Web Pushやバックグラウンド通知を必須にせず、通知が届かない場合も画面の再読込み・結果照会で確認できる。

PAY-B06　承認前に店舗・金額・商品明細を変更した場合は旧要求を取消し、別要求で確認し直す。別イベントの支払QR、期限切れ、権限なし店舗、他人の承認要求を拒否する。[S9]

## 13　QR決済A・C方式と読取り条件

PAY-A01　A方式は会計ごとの店舗QR。店員が商品・金額を確定した会計を作り、店舗スマホに表示する。利用者が読み、イベント参加と本人確認を満たした後に店舗・金額を確認して承認する。

PAY-A02　会計QRは120秒有効。同一会計を複数人が読んだ場合、最初に本人への関連付けが成立した利用者だけが承認可能。他者には「確認中／支払済み」を表示する。関連付け済み利用者が拒否した場合、同じQRを他者へ使い回さず店舗が再発行する。

PAY-C01　C方式の固定QRは店舗案内用のランダム識別URLであり、金額・残高・支払承認は含まない。印刷を必須設備とせず、店のスマホ画面にも表示できる。固定QRを読んだだけで自動支払いをしない。

| 店舗条件 | 固定QRからの操作 |
| --- | --- |
| 金額管理店舗 | 利用者が金額入力→店舗・金額を確認→承認。店員は自店舗の着金一覧から実額・取引IDを照合。 |
| 商品・在庫必須＋モバイル注文許可 | 商品選択→明細確認→承認。支払いと在庫確保・注文受付を同時成立。 |
| 商品・在庫必須＋モバイル注文禁止 | 店舗案内だけを表示し、店舗レジのA/B方式へ案内。明細なし決済は不可。 |

PAY-C02　金額入力型Cは店舗が要求額を事前固定しないため、不足額・誤額の検出を店員が行う。差額は新たな会計と本人承認で支払い、過払いは元決済への部分返金で訂正する。成立取引の金額を後から編集しない。

QR-01　アプリ内のカメラ読み取りはHTTPSとカメラ許可を前提とする。拒否・カメラ未検出時は操作案内と他のQR方式を提示する。全端末で特定のブラウザAPIが使えるとは仮定せず、読取り実装を実機確認する。[S10]

QR-02　任意の外部URLへ自動遷移するスキャナーにしない。自サービスの許可形式・用途だけを受理し、店舗名と金額を最終画面へ明示する。読取り成功音だけで支払成功を表現しない。

QR-03　QR表示は高コントラスト・余白付き、スマホ縦画面で切れないサイズとする。読取り、表示、結果確認を同じ店舗スマホ1台で切替できる。写真のスクリーンショットを店舗の成立確認の代わりにしない。

## 14　取引成立・再送・通信断の共通仕様

TX-01　決済要求の状態は CREATED → AWAITING_APPROVAL → SUCCEEDED、または DECLINED / CANCELLED / EXPIRED とする。SUCCEEDEDから未成立へ戻さない。返金は元取引を参照する別取引であり、元決済の履歴を消さない。

TX-02　受付期間・権限・アカウント状態・本人承認・対象額・店舗・商品・在庫・残高を、確定時にサーバーで再検証する。利用者が承認した内容の版と一致しない場合は拒否する。[S9]

TX-03　金銭更新は認証主体・イベント・操作に紐づく冪等キーを必須とする。同一キー＋同一内容は同じ結果。同一キー＋異内容は409。取引・キーは台帳保存期間中保持し、キーの失効によって同じ成立要求が再実行されないようにする。

TX-04　残高・売上・注文・在庫・台帳・更新通知用イベントを1つのDBトランザクションで確定する。通知送信・外部メールはコミット後のOutbox処理とし、通知失敗を理由に決済を取り消さない。重複通知は通知IDで抑止する。

| 状況 | 端末の表示・次の操作 |
| --- | --- |
| 未送信で通信不可 | 「通信できないため支払えません」。送信待ちを自動実行キューへ保存しない。 |
| 要求送信後10秒応答なし | 「結果確認中」。失敗と断定せず、元の要求IDで結果照会。新規IDの再支払いを促さない。 |
| 取引ID応答も未受信 | 保存した要求キーを本人認証下で照会し、未成立か成立済みかを解決。ローカルキーは権限の代用にしない。 |
| 成立済み | 同じ取引ID・額・時刻を表示。再読み込み・回線変更でも再減算しない。 |
| 未成立が確定 | 拒否・期限切れ理由を表示。必要なら利用者が改めて新会計へ進む。 |

TX-05　結果照会は最初の30秒は2秒間隔、その後5秒間隔。2分経過後は画面に手動照会も提示し、取引自体は未確認一覧へ保持する。クライアントタイムアウトでサーバー状態を書換えない。バックグラウンドでは不要なポーリングを停止する。

TX-06　DBロック・デッドロック・直列化失敗は同じキーのままサーバー内部で最大3回再試行し、完了不能なら結果照会可能な応答を返す。ロック順を統一し、他イベントの残高をロックしない。選択するロックはDB公式仕様を踏まえ競合試験する。[S11]

## 15　利用者間譲渡・誤送信の扱い

TRF-01　主催者が譲渡を有効化したイベントでのみ利用可能。送信者と受取人は同一イベントの有効な参加者であること。自己宛、他イベント、停止アカウント宛、残高不足、期限外を拒否する。金額・日次累計の業務上限は設けない。

### 操作フロー
| 順序 | 処理 |
| --- | --- |
| 1 | 受取人が「譲渡を受け取る」を選び、120秒有効の受取用QRを表示。 |
| 2 | 送信者が読み取り、表示名と照合番号・イベントを確認。電話番号やメール検索で不特定の宛先を探す機能は持たない。 |
| 3 | 送信者が金額を入力し、送信後残高を確認。「この相手に譲渡する」を明示承認。 |
| 4 | サーバーが最新設定・両参加状態・トークン・金額・残高を再確認し、送信者減算と受取人加算を一括確定。 |
| 5 | 双方が同一取引の額・相手表示・時刻を履歴で確認。 |

TRF-02　1つの受取トークンは1譲渡へ関連付けて消費する。多数の人から受け取る場合は毎回新しいQRを表示する。トークンを恒久的な残高移動権限にしない。送信者の本人承認なしでは成立しない。

TRF-03　1つの譲渡の全額を同時に移動する。相手への加算が失敗した状態で送信者だけ減算すること、資金が宙に浮く中間成功を返すことを禁止する。同一要求の再送・同時承認は1回だけ成立。

TRF-04　成立後の送信者単独取消は不可。誤送信は受取人による新しい譲渡、または主催者への申告・調査で扱う。主催者は本人承認なしに任意の2利用者間で残高を動かす通常操作を持たない。

TRF-05　受取分も現金チャージ分と同じイベント払戻し条件に従う。譲渡由来だけを払戻し不可にする設定は設けない。由来を示す取引履歴は保持するが、由来ごとに払戻し可否の残高を分割しない。

TRF-06　主催者が譲渡をOFFにした後は、作成済み・未成立の要求も確定時に拒否する。すでに成立した譲渡、保有残高、受取人の払戻し資格はその操作だけでは変更しない。連続的な不正操作は金額ではなく認証・頻度・状態により抑止する。

## 16　未使用残高の現金払戻し

CSH-01　イベントで払戻し有効、受付期間内、本人確認済み、十分な対象残高、担当者の払戻し権限・業務認証がある場合に開始する。初期は手数料0円、申出額と交付額は同額。譲渡受取分も同条件で対象となる。

### 状態と現金の手順
| 状態・遷移 | システム・担当者の動作 |
| --- | --- |
| PREPARED | 本人QR読取、額・相手・イベント確認。まだ現金を渡さない。 |
| HELD | 本人が払戻し額を承認。サーバーが利用可能残高から拘束へ振替。1利用者・1イベントの現金払戻し処理は同時に1件。 |
| CASH_HANDING | 担当者が「現金を渡す」を開始。画面に本人・額・取引番号を固定表示。自動取消対象外。 |
| PAID | 現金を交付し、担当者が交付済みを確定。拘束減算、払戻し台帳、監査を一括確定。本人にも結果を表示。 |
| CANCELLED | 現金未交付を担当者が確認できる場合だけ理由付き取消、拘束を解除。 |
| INVESTIGATING | 交付有無・結果が不明。拘束を維持し主催者が調査。再交付・自動解除しない。 |

CSH-02　HELDから5分操作がない場合は警告し、30分で調査対象一覧へ出すが、自動解除しない。CASH_HANDING以降の未完了は即座に調査対象へ表示する。現金の物理的交付はDBと同時確定できないため、担当者・現金実査と照合する。

CSH-03　同一完了要求の再送は1回だけ処理し、交付済みを取り消して現金再交付を要求しない。別担当が引き継ぐ場合は元担当・新担当・理由・時刻を記録する。引継ぎは主催者または払戻し管理権限者が行う。

CSH-04　現金を渡す前に拘束されていることを担当端末で確認する。拘束額は他の決済・譲渡・払戻しに使えない。手続開始後に通常受付時間を過ぎても、その手続の安全な完了・取消・調査は許可する。

CSH-05　現金払戻しをアプリ上の利用者間譲渡で代用しない。プラットフォームから銀行へ送金する機能はない。誤って「交付済み」にした場合は無条件に残高を復元せず、現金調査と理由付き訂正取引を主催者が扱う。

CSH-06　払い戻す現金不足は主催者の未解決案件とする。利用者の権利を消去せず、受付場所・連絡先・対応状況を表示する。制度上の払戻し可否と手続は公開前に確認する。[S8]

## 17　購入取消・部分返金・失効

REF-01　購入取消は元の成立決済を必須とし、元イベント・元支払者にだけ返す。通常の未使用残高払戻しがOFFでも、購入取消の返金を省略しない。主催者、または対象店舗の返金権限者が理由を付けて実行する。

REF-02　金額入力会計は返金額を指定する。商品明細会計は商品と数量を指定し、元の単価で算出する。初期は商品明細の任意値引き返金を行わない。返金累計は元決済額以下、商品別の返金数量は元購入数量以下。並行返金でも超過させない。

REF-03　返金額加算・売上減算・返金明細・台帳・監査は同時成立。同じキーの再送で二重返金しない。返金によって元の支払い日時・金額・支払者・注文明細を上書きしない。

| 返金する時点 | 返金先・使用条件 |
| --- | --- |
| 通常の支払期間内で残高も有効 | 元の利用可能残高に戻す。 |
| 販売終了・残高失効後 | 同じ本人・同じイベントの「返金専用額」へ戻す。支払い・譲渡・自動失効は禁止。 |
| 返金専用額の現金交付 | 通常払戻しOFFや通常受付終了に関係なく、主催者が設定する精算用受付で交付可能。返金作成から30日を案内期間とし、未交付だからといって自動消去しない。 |
| 技術的障害で返金不能 | 未完了返金申出を保持。返金済みにしない。解決まで完了・データ削除を禁止。 |

REF-04　在庫の復元は返金と分離する。調理済み・引渡済みなら自動復元しない。「再販売可能」の確認と理由がある場合のみ、返金済み数量以内で在庫移動を追加する。数量を二重復元できない。

EXP-01　主催者が初回チャージ前に選んだ条件に従い、失効は台帳の別取引として実行する。対象は期限到来時の通常残高で、払戻し拘束・返金専用額・紛争で保全中の額を除く。各口座・条件版・期限に一意の処理キーを付け、再実行で二重減算しない。

EXP-02　通常利用期限後は新規支払い・譲渡を拒否し、失効バッチが遅れたことを利用して使用できないようにする。失効日時と払戻し期間の矛盾は保存時に拒否。残高・履歴の非表示や削除を失効の代わりにしない。

EXP-03　失効後の正当な返金は返金専用額として保持し、既失効残高を再チャージとして復活させない。技術上の失効処理が法的な債権消滅を証明するとは扱わない。[S8]

## 18　商品・価格・在庫管理

PRD-01　商品は店舗に所属し、名称1～100文字、説明0～1,000文字、正の円価格、販売状態、表示順、在庫管理有無、任意画像を持つ。価格は利用者の支払総額とする。税率計算・適格請求書の発行機能は初期対象外。

PRD-02　商品の価格・名称・提供条件は会計作成時に版付きで保存する。支払確認開始時の版を120秒有効の見積として固定し、その間の通常の価格変更を無断適用しない。販売停止・安全上の停止は未成立見積も無効化する。過去明細は商品編集で変わらない。

| 項目 | 在庫の定義 |
| --- | --- |
| 手元在庫 on_hand | 未販売の商品数量。非負整数。 |
| 予約 reserved | 未払いの支払確認に引当て中の数量。0≦reserved≦on_hand。 |
| 販売可能 available | on_hand－reserved。カートに入れただけでは減らさない。 |
| 支払い確定 | on_handとreservedを同じ数量減らし、販売記録へ移す。 |
| 予約失効・取消 | reservedだけ解放。支払成立済みなら解放しない。 |
| 入荷・廃棄・訂正・再販戻し | 在庫移動の別記録として理由と実行者を保存。 |

INV-01　在庫は商品単位。支払確認開始時に必要な全明細を一括予約し、有効120秒。1明細でも不足なら残りを部分予約せず全体拒否。同一注文で予約を重複作成しない。

INV-02　期限切れ予約は5秒間隔の処理を基本に解放し、在庫確認時にも期限を評価する。期限切れと支払い確定は同じ予約・在庫行をロックして排他制御し、販売と解放の両方を成立させない。

INV-03　利用者・イベント・店舗単位で支払確認中カートは1件、1注文50明細まで、1商品数量1～999を資源保護・誤入力防止の基準とする。これらは金額上限ではない。通常の在庫数量は32ビット非負整数の範囲で管理し、範囲外を拒否する。

INV-04　手動在庫減算は予約済み数量を下回らせない。予約を先に安全に取消すか、訂正を拒否して必要な対応を表示する。商品の削除は未販売・参照なしに限り、取引済みは販売停止・アーカイブで保持。

INV-05　最後の1個を複数レジとモバイルが同時購入しても成立は最大1件。キャッシュ上の在庫を決済確定の根拠にしない。

## 19　注文・モバイルオーダー・受渡し

ORD-01　店員入力・モバイル注文は同じ注文モデルを使用し、注文経路を別項目で記録する。モバイル注文は主催者と店舗の双方許可、受付中、有効商品、十分な在庫が条件。前払い・決済成立時の自動受付とし、店舗の事前承認待ちは設けない。

| 状態 | 許可する遷移・処理 |
| --- | --- |
| 支払待ち | 支払成立→受付済み。未成立取消・期限切れ→取消。調理対象にはしない。 |
| 受付済み | 調理・準備中、または準備不要なら受取待ち。全取消・部分返金を別記録で処理可能。 |
| 調理・準備中 | 受取待ち。提供不能なら取消返金へ進める。 |
| 受取待ち | 本人受取照合→受取完了。未受取を理由に自動完了・自動失効しない。 |
| 受取完了 | 通常の進捗更新は終了。正当な返品・返金は元決済を参照した別処理。 |
| 取消 | 未払い取消は金銭移動なし。支払済みの全取消は全額返金の完了または要調査状態と対応付ける。 |

ORD-02　支払状態、提供状態、返金状態を分離する。部分返金でも残る商品があれば提供を続ける。元注文を「未払い」に戻して返金を表現しない。複数店舗カート、後払い、配達、時間予約、利用者による支払後の無条件取消は初期対象外。

ORD-03　注文番号はイベント・店舗内で重複せず、日付・連番等で読み上げ可能とする。注文の内部IDとは別。取引時点の商品名・単価・数量・総額・版を固定保存する。

ORD-04　受渡しは受付番号に加え、本人の受取画面・受取用QRまたは照合コードを確認する。受取QRは署名なしの連番だけにしない。短い照合コードは8桁、失敗5回／注文／10分で保留し、店員が本人画面を再確認する。コードは受取時に失効。

ORD-05　受取完了は店舗の権限者がサーバーで確定する。複数端末の二重受取操作は1回だけ成立。公開の呼出画面へ氏名・メール・残高を表示しない。プッシュ通知・音が出なくても本人画面で状態を確認できる。

ORD-06　商品不足・店舗閉店・イベント中止時は、未成立支払いを取消し、支払済みで未提供の注文を一覧化して返金・提供の選択を記録する。利用者に支払いだけ残したままイベントを完了できない。

## 22　API共通契約・外部連携

API-01　HTTPSのJSON APIを/v1配下へ分離し、認証Cookie、CSRF防御、イベント・店舗・本人の認可を共通処理にする。金額は10進文字列、時刻はUTCのISO 8601、IDは推測困難な不変ID、ページングはカーソルを基準とする。

| --- | --- |

| イベント・参加 | 作成・条件・掲載・参加。戻り値に適用条件版、所属状態、イベント時刻を含める。 |

| 支払要求 | 方式、店舗、明細または金額、会計版→要求ID・期限・承認状態。対象者の結合はサーバー検証。 |

| 取引照会 | IDまたは本人の要求キー→正本の状態。キャッシュ・読み取り遅延で成立を否定しない。 |
| CSV・更新通知 | フィルターと権限の固定、生成時刻、再接続カーソル。通知本文だけを残高正本としない。 |

API-02　共通エラーはcode、message、request_id、retryable、現在状態または照会先を返す。401認証、403権限、404不存在・秘匿対象、409競合／重複内容相違、422入力、429頻度制限、503一時停止を区別する。残高不足・在庫不足・期限切れは機械判定できる業務コードを付ける。

API-03　金銭処理で接続切断時は結果不明になり得るため、HTTPエラーだけで「未成立」を保証しない。照会結果が最終拒否の場合のみ新要求へ案内する。成功応答はDBの永続化完了後に返す。

API-04　OpenAPIで要求・応答・権限・状態・エラーを定義し、フロントとバックで型を共有する。過去アプリからの要求も認証・金額・版を再検証し、必須改訂時には更新案内を返す。

API-05　外部連携はGoogle認証と認証メール配送を初期対象とする。決済会社・銀行・NFC・POS専用機の接続は不要。外部サービスの成功／障害と内部金銭成立を混同しない。

## 23　台帳・不変条件・整合性

LED-01　成立した金額移動は取引ヘッダと2本以上の台帳明細に記録し、同一取引の符号付き明細合計を0にする。イベント内の勘定を閉じ、他イベントの明細を混在させない。確定済み台帳は通常機能で編集・削除しない。

| 取引例 | 増える側／減る側（符号は台帳の定義に統一） |
| --- | --- |
| 現金チャージ | 利用者利用可能額＋、主催者現金受領対応勘定－。 |
| 支払い | 利用者利用可能額－、店舗売上勘定＋。 |
| 譲渡 | 送信者利用可能額－、受取人利用可能額＋。 |
| 現金払戻し拘束 | 利用者利用可能額－、払戻し拘束＋。 |
| 現金払戻し完了 | 払戻し拘束－、主催者現金交付対応勘定＋。 |
| 購入取消返金 | 店舗売上勘定－、元利用者の利用可能額または返金専用額＋。 |
| 残高失効 | 対象利用者残高－、失効勘定＋。 |

LED-02　利用者利用可能額・拘束額・返金専用額と、商品の販売可能在庫は常に非負。譲渡で利用者残高総額は変化しない。返金累計は元決済以下。金銭確定・注文成立・在庫販売が分離した成功状態は0件でなければならない。

LED-03　口座残高は台帳から再計算できる。高速参照用の残高行を持つ場合は同一トランザクション内で更新し、台帳と定期照合する。イベント総額をすべての決済で1つの行へ更新する構造は避け、集計の競合を抑える。

LED-04　全更新は同一DBのトランザクション、口座・在庫行のロック、条件付き更新、一意制約を組み合わせる。残高を読んだ後に別トランザクションで減算する実装は禁止。ロック順はイベント制御・権限、口座ID、商品ID、要求IDなどで一貫させる。[S11]

### 終了時の照合式
チャージ純額－現金払戻し額＝利用者残高総額＋店舗売上純額＋失効額。チャージ純額は元チャージから誤チャージ訂正を差し引く。利用者残高総額には拘束・返金専用額を含む。店舗売上純額は決済額－購入取消返金額。

LED-05　例：1,000円チャージ→AからBへ200円譲渡→Aが600円支払→100円購入取消返金→Aが100円現金払戻し。利用者残高合計400円、店舗売上500円。左辺900円＝右辺900円。譲渡200円を売上・発行残高へ二重計上しない。

LED-06　金額照合は5分ごとの増分検査と日次全件、イベント完了前の全件検査を行う。不一致は当該イベントの新規金銭処理を停止し、原因確認・訂正と再照合後に再開する。

DAT-01　event_idを持つ関連データは複合外部キー等で所属一致を保証する。別店舗の商品IDと支払要求を混在させない。金銭履歴の外部キーは削除連鎖させず、取引済み親データはアーカイブする。

DAT-02　取引はevent＋account＋時刻、event＋shop＋時刻、元取引、冪等キーで索引を用意する。在庫はshop＋product、注文はshop＋state＋時刻を基準に検索計画を確認する。全履歴の無条件スキャンを主要画面の都度処理にしない。

DAT-03　数値・時刻・保存先の正本はサーバー。秘密トークンは通常ログに出さず、商品画像等のファイルキーはイベント・店舗に紐付けて所有者を検証する。個人IDを公開URLに連番で露出しない。

## 25　売上・CSV・現金照合

RPT-01　期間・イベント・店舗別に成立決済件数、決済総額、返金額、売上純額、商品数量、注文経路別売上を集計する。チャージ・譲渡・未使用残高払戻しは店舗売上に含めない。受付担当別には現金受領・交付・未解決件数を表示する。

| 出力 | 必須項目 |
| --- | --- |
| 取引CSV | event_id、shop_id、transaction_id、original_transaction_id、type、state、amount_yen、occurred_at、timezone、order_id、operator_id。 |
| 店舗集計CSV | イベント・店舗ID、店舗名、期間、成立件数、gross_sales_yen、refund_yen、net_sales_yen、generated_at、snapshot_id。 |
| 現金照合CSV | 担当者、受付場所、受領額、交付額、誤チャージ訂正、実査額、差異額、差異理由、未解決処理数。 |
| 注文明細CSV | 店舗、注文、経路、商品ID、時点名称・単価、数量、返金数量、提供状態。 |

RPT-02　日時の期間は[start,end)、タイムゾーンは日本時間を既定とする。売上は決済確定時刻、返金は返金確定時刻で期間集計し、元決済期間の再集計版も区別して出力する。後日の返金で過去CSVを無言で書換えない。

RPT-03　CSVはUTF-8 BOM付き、CRLF、正しい引用符エスケープ。文字列の先頭に=、+、-、@、タブ、改行等がある場合は表計算ソフトの式実行を防ぐ処理を行う。メール・認証秘密・QR秘密を出力しない。

RPT-04　金額は数字文字列を保持し、大桁を表計算ソフトが丸め得る点を出力説明に明記する。CSVを正本にしない。10万行以内を1ファイル、超過時は連番で分割。1利用者の生成は2件まで同時実行し、出力物は24時間で削除、ダウンロード認証を毎回確認する。

RPT-05　生成開始時点のスナップショット・条件・権限を記録し、同じCSV内で前後の集計時点を混在させない。完了後も返金が発生したら新しいsnapshot_idで再出力する。

CSH-07　現金の理論額は開始釣銭＋記録済み受領－記録済み交付－記録済み返却等で算出し、現金移動は別記録を用いる。実査額との差を理由付き保存し、差異0と未解決案件0を終了条件とする。釣銭投入を利用者チャージと混同しない。

RPT-06　初期精算は売上集計・CSVまで。出店料・手数料控除、自動振込、支払済み保証、銀行口座情報の収集はしない。実際の店舗支払いは主催者がシステム外で行う。

## 26　通信・PWA・対応端末

NET-01　全業務はクラウドの正本へ接続して確定する。会場サーバーを要求せず、Wi-Fi・携帯回線を問わない。認証や不正対策の通信保護は行うが、会場IPホワイトリスト・LAN運用は機能として持たない。

NET-02　ブラウザ再読込み、Wi-Fiから携帯回線、同アカウントの端末交換でも同じ要求IDの結果を照会する。未送信金銭要求をBackground Sync等で自動再実行しない。オフライン時は未更新残高に確認時刻・通信不可を表示する。

PWA-01　Webの通常利用を必須とし、ホーム画面追加は余力対応。Service Workerを使う場合、静的アセットだけを版付き保存し、認証・残高・金銭・注文APIはnetwork-only／no-storeとする。個人APIを共有キャッシュへ保存しない。

PWA-02　更新は画面に通知し、金銭処理中・結果確認中・現金交付中の強制再読込みを禁止する。API非互換時は安全な停止と既取引照会を優先し、更新後に同じ取引へ復帰する。古いフロントの要求でも金額・権限・版の検証はサーバーで行う。

| 対象 | 対応基準・試験条件 |
| --- | --- |
| 来場者・レジ | iPhone Safari、Android Chromeの正式サポート中の現行系統と直前系統を基準。2026年12月1日に具体版を試験台帳へ固定し、公開前のセキュリティ更新を再確認。 |
| PC管理 | WindowsのChrome／Edge、macOSのSafari／Chrome。公開判定時の安定版で検証。 |
| 実機 | iPhone・Androidを各最低2構成（新しめ＋チームが用意できる旧め）。来場者／店舗を入れ替えてB/A/C、カメラ、再ログインを確認。 |
| 非対応 | IE、ガラケー、更新終了OS、JavaScript無効、カメラ非搭載端末の読取機能、アプリ内WebViewの動作保証。外部ブラウザへ案内する。 |

NET-03　「すべてのスマホで無条件に利用可能」とは表現しない。必要条件と実機一覧を公開し、外部カメラからのA/Cアクセスも検証する。実機の一部が未確保なら、その試験項目を未実施として残す。

NET-04　画面のライブ更新はSSE＋再接続を基準とし、通知は変化の案内だけにする。再接続後は正本の差分・現在値を再取得。注文5秒以内・残高と決済結果2秒以内の通常時画面反映を目標とする。

## 27　性能・負荷試験の合格基準

数値は補完採用する受入目標であり、未測定。無料の開発環境や設計だけで対応能力を保証しない。契約・許可のある自分たちの試験環境で実施する。

| 要件 | 試験条件・合格基準 |
| --- | --- |
| PERF-01 データ | 3イベント、各1万人・100店舗・200レジ、各5万件の過去決済。総3,000閲覧セッション＋600レジを用意。 |
| PERF-02 通常負荷 | 1イベント30決済／秒、全体90決済／秒を60分。レジ200台が10秒に1回＝20件／秒、モバイル10件／秒を加えた試験仮定。 |
| PERF-03 複合負荷 | 各イベントでチャージ5件／秒、譲渡5件／秒、返金1件／秒、参照200要求／秒を通常決済に加える。単一ユーザーへ負荷を集中させる別試験も行う。 |
| PERF-04 瞬間負荷 | 決済60件／秒／イベント、合計180件／秒を5分。処理待ち・429等で保護しても二重処理・金額不一致0。 |
| PERF-05 サーバー | 通常負荷で金銭確定APIはp95≦1秒、p99≦3秒。プロキシ受信～DBコミット・応答までを計測。 |
| PERF-06 画面 | RTT100ms、下り10Mbps・上り2Mbps、損失0.1%の試験条件で、最終承認～結果表示p95≦2秒、p99≦5秒。人のQR操作時間は除外。 |
| PERF-07 正確性 | 二重減算、負残高、返金超過、二重売上、在庫過売、台帳不一致はいずれも0件。速度達成でも1件の不整合で不合格。 |
| PERF-08 失敗率 | 通常複合負荷で有効要求の最終技術失敗率0.1%未満。429も有効要求への誤制限なら失敗に含める。残高不足等は別集計。 |
| PERF-09 初回表示 | 来場者ホーム・レジは上記回線の実機で主要操作が3秒以内に利用可能。画像の遅延読込で金額操作を妨げない。 |
| PERF-10 一覧・CSV | 通常負荷で履歴50件取得p95≦1秒、10万行CSVは120秒以内。集計処理が決済を停止させない。 |

PERF-11　受付集中を想定し、イベント参加50件／秒／イベントを5分、ログイン・招待・認証メールの配送制限を別試験する。外部Google認証の大量負荷試験は勝手に行わず、内部契約試験と実認証の少数実機試験を分離する。

PERF-12　CPU、メモリ、DB版・接続数、索引、ネットワーク、データ件数、ビルド、コミット、生成機器、全リクエスト経路、p50/p95/p99、実効スループット、エラー内訳を報告する。90決済／秒はHTTP90要求／秒と同義でない。

PERF-13　未達の場合は構成・クエリ・索引・通知を改善し再測定する。未達の目標を勝手に下げず、必要なスコープ変更は変更記録で明示する。

## 28　セキュリティ・レート制限・ファイル

SEC-07　SQLはパラメーター化、出力は文脈別エスケープ、Cookie認証の更新系にCSRF検証、許可OriginのみCORS、CSP・HTTPSを設定する。APIでevent／shop／accountの所属を検証し、他者のIDを知ってもデータを取得・操作できないようにする。[S1]

| 操作 | 初期の頻度制御値（調整は性能試験で記録） |
| --- | --- |
| ログイン失敗 | 識別子＋端末で10回／10分、15分待機。IPだけを唯一の遮断条件にしない。 |
| パスワード再設定 | 1分間隔以上・宛先5回／時。外部へ登録の有無を露出しない。 |
| 参加パスワード | アカウント＋イベントで10失敗／10分、15分待機。 |
| 金銭更新・会計作成 | アカウント＋イベント＋業務端末で60回／分、瞬間10回まで。取引照会は別枠。 |
| 一般参照 | アカウント＋セッションで300回／分、瞬間30回まで。SSEは1アカウント10接続。 |
| スタッフ招待 | 発行者＋イベントで30回／時。対象者・ロールの重複発行は再発行へ。 |

SEC-08　同一Wi-Fi・携帯キャリアの共用IPで多数の正規利用者が利用する試験を必須とする。429はRetry-Afterを返し、別要求への変更を促さない。認証失敗は識別子全体にも集約し、端末IDの変更だけで制限を回避させない。共用IP全体の一律停止は避け、全体の攻撃対策を会場接続元制限と混同しない。

SEC-09　画像はJPEG/PNG/WebP、1ファイル5MB以下、画像の実体・寸法・ピクセル数を検証し、長辺2,048px以下へ再エンコードする。EXIFを除去、SVG・HTML・実行ファイルは拒否する。1店舗の商品画像を1,000枚以内とし、超過時は整理を案内する。外部URLからサーバーが任意取得する機能は作らない。

SEC-10　認証トークン、TOTP秘密、招待URL秘密、パスワード、回復コードはログ・解析・CSVへ送らない。ログに必要なID・相関IDだけ記録し、アクセス権と保存期間を制御する。公開エラーにスタックトレース・DB接続情報を出さない。

SEC-11　依存関係・秘密情報検査をCIに組み込む。公開前にID改ざん、権限昇格、XSS、CSRF、QR再利用、メール連携乗取り、同時更新、負荷による誤制限を試験する。未解決の重大な金額不整合・越権・認証欠陥は公開不可とする。

## 29　保存期間・個人情報・退会

PRV-01　収集目的は認証、イベント参加、金銭・注文処理、問い合わせ、不正対策、監査に限定する。氏名住所・生年月日・身分証・カード番号は初期機能では収集しない。法務確認で追加本人確認が必要となった場合は変更要件として公開前に対応する。

| データ | 補完採用する保存基準 |
| --- | --- |
| 台帳・金銭取引・条件版・精算根拠 | イベントの全残高処理完了から7年を設計基準とする。法定期間と断定せず、発行主体等の確認により必要期間へ見直す。 |
| 商品名・金額等の注文明細 | 金銭根拠に必要な部分は台帳と同期間。受取QR・呼出用情報は完了30日後に削除・無効化。 |
| 権限・金銭の重要監査 | 関連金銭記録と同期間。通常の認証・セキュリティログは180日、一般アクセスログは30日。 |
| 失効・取消済み招待 | 秘密ハッシュは失効後30日で削除。権限付与の実行者・内容は監査として保存。 |
| CSVファイル・一時画像 | CSVは24時間、未紐付けアップロードは24時間で削除。 |

PRV-02　利用目的・期間・共有先をプライバシー通知に明示する。一般店舗にはメール・他店舗履歴・残高全体を渡さない。表示名も注文受取等の必要範囲に限定する。個人情報保護法に一律の保存年数があるとは扱わず、必要性がなくなった情報の消去を検討する。[S13]

PRV-03　アカウント削除は再認証後に受け付ける。残高・拘束・未完了注文・返金・現金案件があれば通常削除を保留し精算へ案内する。保留はログイン不能化や請求権消去と同義にしない。

PRV-04　精算済みの退会は30日後にプロフィール・連絡先を削除または分離し、残る取引は必要最小限の内部IDへ置換する。内部IDによる履歴は必ずしも匿名情報ではないため引き続き保護する。法的保存・紛争保全の対象は理由と見直し期限を記録する。

PRV-05　復元したバックアップで退会・削除済み情報が復活しないよう、削除・失効記録を再適用する。継続運営しない場合も、保存義務・残高対応を満たす保管主体と問い合わせ窓口を確定してから停止する。

OPS-05　開発は既存PCで日次保存と復元試験を行えるが、本番の冗長化・費用・容量を保証するものではない。バックアップは暗号化・別障害ドメインに置き、鍵の保管とアクセス権を分離する。少なくとも毎月・主要DB変更前に復元試験を行う。

OPS-06　障害時は検知→安全停止→取引ID保全→原因切分け→復旧→台帳・現金照合→主催者判断で再開→記録の順。ログ調査のために成立取引を直接書換えない。DB変更は段階的移行とし、破壊的な自動ロールバックで取引を消さない。
